## How translation works

`text!` is the translation pipeline, and the **whole format string is the catalog key**.
At compile time the macro reads every `i18n/<locale>.toml` file at your crate root and
embeds the translations; at runtime each `text!` resolves against the current locale and
**re-resolves reactively when the locale changes** — no `watch`, no event plumbing.

```rust
text!("Welcome Desk")                 // looked up verbatim as the key "Welcome Desk"
text!("Hello, {name}")                // placeholders are slot keys inside the translation
```

Static strings localize through the same catalog: `text("Welcome Desk")` (a `&'static
str`) looks the literal up in the `TranslationCatalog` installed in the environment at
runtime, so it translates wherever the app installs one — every scaffolded entry point
does, and a hand-built `Environment` (a test, an embedding) gets it from
`waterui::configure_environment!(env)`. `String` and `Str` are never looked up: they are
verbatim text, as is `Text::verbatim(..)`. `text!` adds what runtime lookup cannot:
`{placeholder}` interpolation, CLDR plural selection, and translations embedded into the
calling crate itself. A plural entry is reachable only through `text!`; a runtime
`text("..")` lookup that lands on one panics. A key with no entry falls through to the
literal, so untranslated apps behave identically — adding the `i18n/` directory is the
only setup step; `water`-generated backend crates embed the project's `i18n/` too.

`Text::localized_or(key, fallback)` looks `key` up in the catalog and falls back to the
`fallback` string rather than the key — for chrome that must read as a real word with no
catalog. `Text::localized_with(|env, locale| TextConfig)` builds text from any
locale-aware resolver — a `'static` `Fn(&Environment, &Locale) -> TextConfig`, need not
be `Send` — and re-runs it when the locale changes.

Numeric arguments interpolate in the locale's digits and separators and every argument
is bidi-isolated; a Rust format spec after the name works (`{blur:.1}`).

Two views can need different translations of one word: `text!("Open" @ menu)` /
`text!("Open" @ "file")` append the context to the key (`"Open#menu"`, `"Open#file"`).

## The catalog files

One TOML file per locale, named by BCP-47 tag, in `i18n/` next to `Cargo.toml`:

```
my-app/
├── Cargo.toml
├── i18n/
│   ├── en.toml          # last resort for every locale
│   ├── en-GB.toml
│   ├── zh.toml          # Simplified: zh, zh-CN, zh-SG
│   ├── zh-Hant.toml     # Traditional: zh-TW, zh-HK
│   └── ja.toml
└── src/lib.rs
```

Inside, keys are the exact source strings:

```toml
"Welcome Desk" = "Welcome Desk"
"Hello, {name}" = "Hello, {name}"

# Long passages get a $-prefixed short key instead of a paragraph-as-key.
"$about_blurb" = "WaterUI is a cross-platform UI framework…"

# Plural keys map to a table of CLDR plural categories.
"I have {#count} passport stamp" = { one = "I have {count} passport stamp", other = "I have {count} passport stamps" }
```

`$`-keys are referenced as `text!("$about_blurb")`; a context key is the string plus
`#context` (`"Open#menu" = "Open"`).

Lookup walks the locale's CLDR fallback chain, which never crosses scripts: `zh-TW` →
`zh-Hant` and stops, so `zh.toml` (Simplified) never serves Traditional Chinese; `zh-CN`
→ `zh`; `sr-Latn` stays apart from `sr-Cyrl`. When the locale is the system one, the
user's other preferred languages are tried next, then `en`. Keep an `en.toml` as the
last resort.

## Plurals

The `{#name}` sigil marks the placeholder that drives plural-category selection:

```rust
text!("I have {#count} passport stamp", count = stamp_count)
```

Rules: the `#` appears only in the *key*; inside each category's value the variable is
written plain (`{count}`). The argument binds with `name = expr` like any aliased slot.
Which categories a language needs comes from CLDR — `one`/`other` suffices for English,
while Russian also needs `few`/`many`; write the categories the target language uses
(`zero`, `one`, `two`, `few`, `many`, `other`; `other` is required and non-empty).

Two plural placeholders in one key select by both counts; the table is keyed
`one_one` / `one_other` / `other_one` / `other_other` (first name's category, then the
second's; `other_other` required):

```rust
text!("{#files} in {#folders}", files = file_count, folders = folder_count)
```

```toml
"{#files} in {#folders}" = { one_one = "{files} file in {folders} folder", one_other = "{files} file in {folders} folders", other_one = "{files} files in {folders} folder", other_other = "{files} files in {folders} folders" }
```

## Switching locale at runtime

```rust
use waterui::locale::{Locale, locales};

waterui::regional::set_locale_tag("zh-TW").expect("valid BCP-47 tag");
```

`set_locale_tag` sets the process-wide locale and returns `Result<(), _>` — a bad tag is
an error to surface, not a silent fallback. Every `text!` in the tree re-resolves
automatically; a locale switch is the canonical case that must **not** be implemented
with `watch`. A language picker is therefore just a `Picker` over tag strings plus an
`.on_change(&selection, |tag| ..)` handler that calls `set_locale_tag`.

The locale a view resolves against is the first of: a `Binding<Locale>` in the
environment, a `RegionalContext`, a plain `Locale`, then the process-wide locale (which
follows the system language). `waterui::locale::locale_binding(&env)` returns that
binding.

`waterui::locale` re-exports the `waterui-locale` crate: `locales::` holds `Locale`
constants (`EN`, `EN_US`, `ZH_TW`, `JA`, `AR`, … — `const` values used directly, as in
`Binding::container(locales::JA)`, not types),
`Locale` derefs to its language identifier (`language`, `region: Option<_>`, each with
`.as_str()`), has `canonical_tag()`, and implements `FromStr`, so `"he".parse::<Locale>()`
works and its failure is handled, not ignored.

## The system locale

The device language is the app's locale from the first frame and follows system changes
with no code. Apple installs a `Locale`, a `RegionalContext` and a `Binding<Locale>` in
the environment; Hydrolysis installs none and `text!` falls through to the process-wide
locale. So read it with `locale_binding`, which works on every backend and is a signal:

```rust
pub fn app(env: Environment) -> App {
    let locale = locale_binding(&env);
    App::new(move || scene(locale.clone()), env)
}
```

`waterui::regional::current_settings().locale()` is the same value as a plain snapshot.

## Scoping locale and direction to a subtree

The free function `waterui::env::with(view, value)` (or `view.with(value)`) extends the
environment for one subtree — the idiomatic way to render one panel in another locale or
direction. Scope a locale as a `Binding<Locale>`: a plain `Locale` is read only when no
`Binding<Locale>` or `RegionalContext` sits above it, and the Apple backend installs one.

```rust
use waterui::env::with;

with(text!("Article").body(), Binding::container(locales::JA))   // Japanese glyph selection
with(arabic_panel(), LayoutDirection::RightToLeft)        // RTL for this subtree only
with(with(panel(), Binding::container(locales::AR)), LayoutDirection::RightToLeft)   // both, nested
```

Locale scoping also drives CJK glyph disambiguation: the same codepoint renders with
Simplified, Traditional, or Japanese forms according to the scoped `Locale`. A scoped
locale does not change the layout direction; scope that separately, as above.

## Locale-aware formatting

Formatting lives in `waterui::locale` (the `waterui-locale` crate). Date and time
(`format::date`) are behind the facade's `locale-datetime` feature and `LocalizedList`
behind `locale-list`, both default-on; number, percent, currency and units are always
there. The functions are plain value-in, `String`-out — so to keep output live, map over
a locale signal and interpolate:

```rust
use waterui::locale::LocalizedDisplay;                      // trait import required
use waterui::locale::format::date::{DateStyle, SimpleDate, format_date};
use waterui::locale::format::unit::{Length, Meter};

let date = locale
    .map(|l| format_date(&l, &SimpleDate::new(2026, 3, 20), DateStyle::Long))
    .computed();
let distance = locale
    .map(|l| Length::<Meter>::new(1500.0).to_localized_string(&l))
    .computed();
vstack((text!("{date}"), text!("{distance}")))
```

`SimpleDate::new(y, m, d)` / `SimpleTime::new(h, m, s)` are lightweight value types
(independent of `jiff`) with `DateStyle` / `TimeStyle` (`Short`, `Medium`, `Long`,
`Full`) for `format_date`, `format_time` and `format_datetime`;
`format_datetime_with_regional_context(&ctx, ..)` takes a `RegionalContext` and
additionally applies its timezone. Unit types — `Length<U>` over `Meter`, `Kilometer`,
`Feet`, `Mile`; `Temperature<U>` over `Celsius`, `Fahrenheit`, `Kelvin`; `Mass<U>` over
`Kilogram`, `Gram`, `Pound`, `Ounce`, all in `format::unit` — render in their own unit
with the locale's digits and unit symbol; they do not switch measurement system, so convert explicitly
(`Length::<Kilometer>::new(42.195).to::<Mile>()`). Rendering them needs the
`LocalizedDisplay` trait in scope. Siblings at the crate root: `format_number`,
`format_percent`, `format_currency(&l, amount, Currency::USD)`, and
`LocalizedList(&["a", "b", "c"])` for a locale-correct "a, b, and c".

`waterui::regional::current_settings()` returns the ambient `RegionalContext` (locale,
timezone, regional preferences) as a plain value, **not** a signal — to react to locale
changes, derive from a locale signal and call it inside the `.map`, as above.

## Right-to-left layout

`LayoutDirection` (`LeftToRight` / `RightToLeft`, in the prelude) is an environment
value. `App::new` derives it from the locale and tracks locale changes, so an Arabic or
Hebrew device mirrors with no code (`waterui::locale::layout_direction(&locale)` gives
the same answer for a `Locale`). Override it by inserting a `LayoutDirection`,
`Binding<LayoutDirection>` or `Computed<LayoutDirection>` into the environment before
`App::new`, or for one subtree with `with(view, direction)` — there is no
`.direction(..)` modifier.
Under RTL, `hstack` child order and `Leading`/`Trailing` alignment are *logical* and
mirror automatically. Never hand-swap children or hardcode left/right for RTL; if
mirrored output looks wrong, the fix is in the view's use of leading/trailing semantics,
not a direction-conditional layout.
